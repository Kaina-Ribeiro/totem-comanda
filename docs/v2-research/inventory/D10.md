## Notes

### Contradictions in the chunk
- Charges (FEAT-048) vs `docs/plan-next.md` decision 16: rule 4 keeps service charges and delivery fees in scope, but decision 16 says no fee on the order for the pilot. All charge rows are `?` until Kai decides.
- Tax groups: rule 1 keeps TAX groups with per-channel rates. `docs/plan-next.md` cuts "tax groups per service". Tax rows are marked IN; Kai to confirm.
- Tax rate: CFG-419 treats rates as entity references, but MODELS 5.16 says a tax rate is not an entity and is never linked.
- Tax rate name: CFG-423 "Display Name" and CFG-424 "Name" both map to MODELS' single `name` field.
- CFG-430 "Tax ID" has a label for a seller ID but an effect text that describes a tax-group link (copied from CFG-416).
- Three fields are labelled "Display text" (CFG-317, 318, 319) with three different meanings.
- "Maximum order to apply" has two meanings: offers (CFG-364) cap the discount, and charges (CFG-410) set an upper basket threshold. FEAT-044 lines 21-23 confirm the offer meaning.
- Order service choices differ: CFG-322 offers All, Collection, Delivery, Seat, but CFG-372 (offers) and CFG-413 (charges) offer only All.
- Legacy offers (FEAT-044) and the current offer editor (FEAT-045) carry the same fields under different ids. Duplicates: CFG-333/353, 336/370, 334/351, 316/354, 317/356, 318/376, 312/355, 327/375, 311/352, 319/357. Only one editor should be built; Kai to choose.
- "Credits" (FEAT-046) are never defined. They could be store credit (gift card, cut), points (PSEUDO_CURRENCY, cut) or a discount.
- Awards (FEAT-047) may be loyalty awards (cut) or CODE, PROMOTION or ITEM awards (in). MODELS Award.type covers both.
- The "Selos" screen in Comanda is item badges (plan-next), not loyalty stamps. Do not confuse the two names.

### Unknowns the spec admits
- Backend redemption, stacking and cross-currency behaviour are Unknown (offers, line 31).
- Backend fee ordering and tax calculation are Unknown (charges, line 42). Exact tax computation is Unknown (line 48). Seller field semantics beyond the controls are Unknown (line 52).
- Code max 50 has a nonstandard validation attribute, so enforcement is not claimed (offers, line 10).
- "Six-place adjustment" for stored percentages (CFG-421 to 426) is not defined further.

### What the v2 models cannot express
- **Promotion definitions.** Discount (8.4) and Award (8.10) are results the POS returns, not rule definitions. Missing: min basket and max discount (CFG-329, 330), dates (CFG-323, 324), basket, section and tag targets (CFG-316, 320, 337), once per order (CFG-332), order-service and payment eligibility (CFG-314, 315, 322), usage limits and first purchase (CFG-326 to 328), display flags (CFG-317, 318, 356, 376). Decision for Kai: where these rules live. CLAUDE.md says the Core API decides discounts, so the rule needs a Core entity (contract change, partner approval).
- **ServiceCharge (8.5)** holds an amount only. It cannot express a percentage (CFG-394, 401), item, section or tag targets, once-per-order, min or max basket, dates, a tax link, or an internal name apart from the customer name.
- **Customer (8.6)** has no account or first-purchase flags, so guest, first-purchase and specific-customer rules (CFG-326 to 328, 334, 351, 360, 379, 386) cannot be checked.
- **Event** (CFG-321) and **internal description** (CFG-363, 408) are not in MODELS.
- **bookingTax** (5.16) has no spec row. Bookings are not in the cut list; decide whether they exist.

### Model drift seen while mapping (8.11-8.13, 9.4, 9.8)
- Totals request uses `discountTotal` and `taxTotal`. Totals response uses `discount` and `tax`. Pick one spelling for the Core contract.
- Totals response discounts carry `locked`, which Discount (8.4) does not define.
- Totals response order items use `price`. The request examples use `itemPrice`. (8.2 is not in my read set; this comes from the examples.)
- DiscountRequest has no "codes to add" field. An entered code goes in `awards` with type CODE. `codesToRemove` removes codes. DiscountResponse (9.8) returns only the applied awards. `discount/cancel` returns an empty body.
- Payment appears only at submit (8.12). Card and cash eligibility (CFG-314, 315) can be checked only at submit, not in totals.
- Percentages are fractions in MODELS (0.20). The spec's six-place rounding rule has no counterpart in MODELS.
- Money: the spec uses decimal BRL (max 99999999.99), which matches rule 1.
